# 压测与单机容量

对应设计文档 6.3（下行 ≤ 2 KB/s/人）与路线图「压测 10,000 人同时在线不掉线」。

## 怎么跑

```bash
# 被测服务（单独的数据目录，开 admin 以读取服务端指标；关掉推播排程）
PORT=8790 ADMIN_TOKEN=lt DATA_DIR=/tmp/lt PUSH=off node server/index.js
# 压测：N 个香客分在多个 worker 线程，30% 走动、其余入座静坐，偶尔礼拜 / 上香 / 合掌
node tools/loadtest.mjs --url http://localhost:8790 --clients 4000 --seconds 40 --admin lt --ramp 400 --workers 10
```

报告三部分：
- **用户感受**：每人每 5 秒一次 ping 穿过房间的往返时间（p50 / p95 / p99 / max）、连接失败与中途掉线数。
- **网络**：每人每秒下行字节（设计预算 ≤ 2 KB/s）。
- **服务端**（`GET /api/admin/stats`，带 `?reset=1` 重开窗口）：事件循环延迟、房间 tick 耗时、收发消息数、存储落盘耗时与写入量、内存。
  `METRICS_LOG=1` 时服务端每 30 秒打印一行（会重置窗口，压测时不要同时开）。

## 结果（2026-11-10，单进程，同一台机器跑压测端与服务端）

机器：Intel i5-14600KF（20 线程）、17 GB 内存、Windows 10、Node 26。服务端是单线程，压测端与它抢同一颗 CPU，所以线上专用机器只会更好。

## 找到并修掉的瓶颈

1. **存储每次落盘重写整个集合**（`users.json`）。写入量随「注册过的人数」线性增长，与在线人数无关；10 万注册用户时每 0.5 秒就要序列化数十 MB，会卡住整个服务。改为**追加日志**：每次只追加改动过的文档，日志超过快照大小时才合并（`server/store/jsonStore.js`）。8,000 人时写入量降到原来的 1/46，单次落盘平均 9.7 → 0.4 ms。关机时完整合并一次；崩溃时最后半行会被跳过。
2. **广播时每个收件人各编码一次 WebSocket 帧**。改为每房间编码一次、同一个 Buffer 写给所有人（服务端帧不加掩码，内容完全相同）。

## 结论与上限

- **单进程实测 10,000 人同时在线、持续 5 分钟零掉线**（ping p99 ≈ 100 ms，tick 最大 9 ms，内存稳定在约 360 MB，没有泄漏迹象）；设计文档估的「单实例约 2,000 人」偏保守。路线图「压测 10,000 人同时在线不掉线」在单进程上达成。
- 首先碰到的限制会是**出口带宽**：每人约 2 KB/s，8,000 人 ≈ 16 MB/s ≈ 130 Mbit/s。选云主机时按「同时在线 × 2 KB/s × 1.5」预留带宽。
- 下行接近 2 KB/s 预算的上沿，是因为压测设定 30% 的人一直在走动；真实大殿里多数人静坐，会更低。
- 本机压测端最多约 16,000 个出站端口（Windows 动态端口范围），连续跑大压测要等 TIME_WAIT 释放（约 2 分钟）。**10,000 人以上要用多台压测机**。
- 压测走的是本机回环网络，没有真实网络的延迟与丢包；上线后用另一台机器、真实网络再测一次。
- 单进程撑得住不等于该只跑一个：为了不在单点上赌，大流量上线（清明）前仍应按 `docs/ARCHITECTURE.md` 换 Redis（房间发现、在线数）+ PostgreSQL，跑 2 个以上实例。
